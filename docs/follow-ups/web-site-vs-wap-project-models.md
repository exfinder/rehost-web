# Web Site vs Web Application Project models

The WAP model is the primary compatibility target and
[Milestone 1](../../ROADMAP.md#current--milestone-1-stock-visual-studio-application)
owns its first package-built application gate.

## The two models

Classic ASP.NET shipped two project models with different compilation
ownership:

| | Web Site (this repo's fixtures and sample) | Web Application Project (WAP) |
| --- | --- | --- |
| Page code | `CodeFile="X.aspx.cs"` — the runtime compiles the code-behind *with* the page, as partial classes | `CodeBehind="X.aspx.cs" Inherits="App.X"` — MSBuild compiles code-behind into the project assembly in `bin`; the runtime only resolves `Inherits` from referenced assemblies and never sees the `.cs` |
| Designer half | None — the runtime generates control fields | `X.aspx.designer.cs`, generated by Visual Studio, compiled into the project assembly |
| `App_Code` | Runtime-compiled into its own assembly | Forbidden (the CS0433 double-compilation trap; VS warned) |
| Global.asax | Inline `<script runat="server">` | Thin marker + `Global.asax.cs` in the project assembly |
| Resources | `App_GlobalResources` runtime-compiled | `.resx` compiled into the assembly by MSBuild, `Properties.Resources` style, though `App_GlobalResources` also worked |
| `bin` | Runtime output only referenced; may be empty | The application: project assembly plus references |

## Current state

Every exercised slice is the Web Site path: `CodeFile` code-behind, inline
`Global.asax`, `App_Code`, runtime-compiled `App_GlobalResources`. The
compatibility map's `CodeFile` row is tested; nothing *tests* `CodeBehind`,
but the sample application's `WapDemo.aspx` exercises it manually and it
works end to end: `CodeBehind` + `Inherits` + designer partial compiled by
the SDK into the host assembly in `bin`, base type resolved from `bin`,
designer fields wired, postback event routed — under a master page. The
model is unassessed, not unsupported; the fixture below is what promotes it.

`Rehost.WebForms.Runtime.targets` already excludes the `App_*` folders from a
consuming host's SDK compile (opt-out
`RehostWebFormsCompileWebSiteFolders=true`), which serves both models — the
folders are runtime-owned in each. It deliberately does **not** exclude
`**/*.aspx.cs`: under Web Site/`CodeFile` those files are runtime-owned and
SDK-compiling them duplicates types, but under WAP they are exactly what MSBuild
must compile. The exclusion decision is model-dependent and waits on this
story.

## Consumer-facing targets

The consumer's build contract now spans two packages: the runtime's
`Rehost.WebForms.Runtime.targets` (also shipped `buildTransitive/`) owns the
lib side — the `App_*` compile/resource exclusions above, the `System.Web`
shim-reference removal, the BinaryFormatter runtimeconfig switch, and the
`RehostAppContentRoot` WAP-style compile glob — while the hosting package's
`Rehost.WebForms.Hosting.targets` owns the exe side: `RehostSiteContentRoot`
staging, the XDT `web.config` pipeline, and the publish site layout. The
hosting staging copies the site **content**; the subtle `App_Code` gap below
remains for anything the content globs exclude: the removes
leave `App_Code` and `App_GlobalResources` in *no* item group at all — the
default `Compile`/`EmbeddedResource` globs claimed them before the removes ran
— so no SDK glob ever publishes them, and `.aspx`/`.master`/`Global.asax`
reach a deployable only because the hosting package's staging copies them as
site content. A Web Site-model consumer whose `App_Code` must ship as source
still has no packaged answer; a `RehostWebFormsPublishWebSitePayload`-style
opt-in would generalize that.

Both the exclusion set and the publish set are blocked on the model decision:
a Web Site host must publish `.aspx.cs` sources because the runtime compiles
them; a WAP host must not compile-exclude or source-publish them because
MSBuild owns them; and a precompiled deployment
([precompiled-deployment](precompiled-deployment.md)) needs no payload at all.
Design the consumer target once, after the model story settles, rather than
accreting per-model patches — and design it WAP-first: the migrated
enterprise WAP is the consumer the packaged targets exist for, and the Web
Site shape is the secondary case even though it is what the repo's own
fixtures exercise.

## What assessing WAP needs

- A fixture with `CodeBehind`/`Inherits` pages whose code-behind and designer
  partials compile into a `bin` assembly, activating `Inherits` resolution from
  `bin` instead of `CodeFile` compilation — the load path WAPs actually use.
- `Global.asax` with `Inherits` pointing at a `bin` type.
- A decision on what the SDK-side build of a migrated WAP looks like: the old
  WAP `.csproj` imported `Microsoft.WebApplication.targets` (designer-file
  generation, `_CopyWebApplication`); an SDK-style replacement needs the
  equivalent item shape, and possibly a `Rehost.WebForms.Sdk`-style template.
- Whether Visual Studio-generated `.designer.cs` files regenerate without
  Visual Studio, or migrated applications freeze them as checked-in source.
- The sample application demonstrates the Web Site model; a second sample —
  or converting the existing one — should demonstrate WAP once it works.

The sibling `../WebFormsApplication` checkout is a Visual Studio WAP template
output and answers shape questions — directive form, designer-file content,
`.csproj` items — without a Visual Studio machine.
