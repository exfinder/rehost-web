# Detailed compatibility reference

Contributor reference for current behavior and limitations.
For an application overview, start with [Will my app work?](../what-works.md).

This is the sole current support map. Detail documents explain mechanisms and
rationale but do not widen these claims.

## Reading the map

- **Supported**: behavior-focused tests pass on Windows x64, Linux, and
  macOS arm64.
- **Partial**: the exact supported boundary and divergence are stated.
- **Unsupported**: deliberately excluded; reached entry points fail explicitly.
- **Unassessed**: present or plausible, but carries no support claim.

## Application and deployment model

| Capability | State | Boundary |
| --- | --- | --- |
| Classic managed request pipeline over Kestrel | Supported | Enters `HttpRuntime.ProcessRequest(HttpWorkerRequest)`; IIS native notification scheduling is not used |
| One application per process/current AppDomain | Supported | Reinitialization and in-process replacement are unavailable; restart means process replacement |
| Request scheme, host, and server variables | Supported | TLS/Host drive scheme, URL, name and port. All 45 Framework variables exist; IIS-only values use fixed single-site shapes or `""`. Native URL variables outside the rewrite contract and `ServerVariables.Set` are unavailable |
| Behind a TLS-terminating proxy or load balancer | Supported | Forwarded For/Proto/Host middleware trusts loopback by default. Other proxies require `ASPNETCORE_FORWARDEDHEADERS_ENABLED=true` or `ForwardedHeadersOptions`; otherwise the app sees proxy values |
| Host registration and activation lifecycle | Partial | Static one-shot bootstrap mutates current-AppDomain state before listen; first-request activation is lazy and shared; bootstrap failure is terminal |
| Runtime-originated shutdown/restart | Partial | Runtime shutdown requests exit code 82 and host stop; a supervisor replaces the process. Host-initiated stop exits normally. Rebuild is eager; requests drain to the host deadline, while new connections wait for replacement. Configuration/file-change causes remain unassessed ([restart ADR](adr/0012-runtime-initiated-restart.md)). |
| `web.config` the runtime cannot parse | Supported with a boundary | 500 with the ASP.NET Configuration Error page naming file and line, followed by exit code 82. IIS refuses undeclared sections natively with 500.19; this runtime renders the managed error page. |
| `Application_Start` failure | Supported | Failure latches: requests during the ten-second window replay 500, including requests waiting for or passing the start lock. Process replacement reruns Application_Start; a cleared fault serves normally. Classic partial-init continuation is not reproduced. |
| Full trust | Supported | Partial trust and CAS policy are unsupported |
| `<httpRuntime targetFramework="4.5" />` or later | Required | Lower values select unassessed quirks and native crypto; startup fails naming the fix |
| `<compilation targetFramework="4.0" />` or later | Supported | 4.x values are inert: the compile surface is the port's own. Values below 4.0 select Framework's multi-targeting machinery and old-compiler probing, which the port has never assessed; startup refuses them naming the value and the floor. An absent attribute keeps Framework's current-version default |
| Web Site runtime-compilation model | Partial | Exercised by fixtures and the sample; consumer build/publish packaging remains incomplete |
| Web Application Project model | Supported | App sidecars compile legacy sources through their own Compile globs over RehostAppContentRoot; Host sidecars stage content through RehostSiteContentRoot. Publish payload and designer policy remain open ([project models](follow-ups/web-site-vs-wap-project-models.md)); real databases and payment responders in sample apps are fixture choices, not additional support claims. |
| Microsoft `System.Web` binary identity | Unsupported | Source/API compatibility after rebuild is the target; strong-name/binary interchangeability is not promised |
| Native ASP.NET/IIS libraries | Unsupported | `UnsafeNativeMethods` fails explicitly when an unported path reaches it |

## Compilation and pages

| Capability | State | Boundary |
| --- | --- | --- |
| Pre-application start, C# `App_Code`, `Global.asax` | Supported | Includes `AppInitialize`, `Application_Start`, generated assembly reuse, and compile-error pages |
| `<codeSubDirectories>` and `App_GlobalResources` | Supported | Neutral resources and one culture satellite are exercised |
| Directory order and `<add assembly="*"/>` | Supported | Listings use deterministic NTFS order on every filesystem. `bin` matches case-insensitive `.dll`, ignores non-assemblies, and fails x86/identity conflicts actionably |
| C# page compilation | Supported | Roslyn provider; default language version 7.3; mapped diagnostics |
| Visual Basic | Unsupported | Configured provider fails with an actionable message |
| Custom CodeDOM providers and advanced batching | Unassessed | Provider options, batch limits, post-processors, and reproducible emission remain open |
| `.aspx` GET, `CodeFile`, common controls | Supported | Parsing, compilation, data binding, URL resolution, request validation, and warm reuse |
| Master pages and user controls | Supported | Nested masters, typed master, runtime `LoadControl`, postback, and basic fragment caching |
| Other controls, config/dynamic masters, and fragment-cache axes | Unassessed | Coverage is not inferred from related controls or runtime master selection |
| `.ashx` | Supported | Direct and Friendly URL handler compilation/execution are exercised |
| `.asmx` serving | Supported | SOAP 1.1/1.2 doc/literal invoke, complex types, headers, faults, sessions, one-way, localhost form POST, `?wsdl`, `?disco`, help page, and `[ScriptService]` JSON are exercised over Kestrel on all three OSes ([web-services-compatibility](web-services-compatibility.md)) |
| `.wsdl` build provider, `App_WebReferences`, encoded `?wsdl` | Unsupported | WSDL→proxy generation needs `System.Xml.Serialization` code-export APIs cut from modern .NET; entry points fail actionably and point at pre-generated clients |
| `Request.Browser` capabilities | Supported | Compiled Framework 4.5 factory includes all 61 definitions. `<browserCaps>` uses `HttpBrowserCapabilities`; unreachable deprecated Mobile controls are the only lost subclass distinction |
| Application `App_Browsers` | Supported | `.browser` files at the folder root and in custom-tree subfolders compile at activation over the built-in factory and extend `Request.Browser`. Every listing is in NTFS order, `*.browser` matches in any casing, and a dot-prefixed file or folder is ordinary. Boundaries: names differing only by `-`, `_` or `'` sort ordinally where Framework's culture sort ignored the hyphen; an edit takes effect at the next process start; machine-wide browser files and `aspnet_regbrowsers` are unsupported ([windows-administration](windows-administration-compatibility.md)) |
| `.xsd` typed DataSets | Unsupported | XSD build-provider generation fails explicitly |
| Precompiled deployment | Unassessed | Imported consumer path exists; neither consumer nor producer is proven cross-platform |
| `System.Web.Extensions` / ScriptManager and UpdatePanel | Supported | IIS-byte-matched async deltas, triggers, Timer, errors and redirects; 13 generated release scripts via `ScriptResource.axd`. Debug/localized resources absent: Auto falls back to invariant release. Recognized browser required ([details](extensions-compatibility.md)) |
| Page methods, `ServiceReference` proxies, profile/authentication/role application services | Partial | ASMX JSON, `/js`, `EnablePageMethods` and disabled-by-default built-in service routes work. Inline proxies compile but are unassessed; enabled provider-backed built-ins unassessed |
| QueryExtender and `QueryableDataSource` | Supported | Expression filtering and ordering over an application `QueryableDataSource` are exercised; `LinqDataSource` is excluded (`System.Data.Linq` has no modern implementation) and fails page compilation naming the missing type |
| Dynamic Data, Entity, Mobile | Unassessed | APIs outside the reached Extensions closure remain absent or unassessed. `System.Web.DynamicData` is not carried, so the Dynamic Data hook every `ItemType` data control calls is inactive rather than fatal |
| Friendly URLs package/API | Partial | Modern package, original public API, routing, caching modes, redirects, authorization, generic handlers, helpers, model binding, mobile pages/masters, and view switching are exercised; advanced escaping and upstream IIS rewrite mapping remain open |
| OWIN host (`Rehost.Owin.Host.SystemWeb`, Katana 4.2.3) | Partial | Startup discovery, module/context and cookie authentication work. StopListening cancels the shutdown token; ClientDisconnectedToken supplies disconnect notification. MapOwinPath/WebSocket upgrade, frames and both close directions work; OWIN close sends without waiting, so middleware must receive the peer's close. Integrated stage markers remain unassessed. |
| Web API 2 (`Microsoft.AspNet.WebApi.*`) | Supported | Rehost.AspNet.WebApi.WebHost replaces the Framework WebHost; Core, Client, Cors, Tracing and Owin remain shipped dependencies. App_Code controller discovery, JSON model binding, JSON 404/errors, no-cache headers and a session-enabled route handler work. SelfHost requires WCF server infrastructure and is excluded. |
| ASP.NET Web Pages (`Microsoft.AspNet.WebPages`, `.cshtml`) | Supported | Rehost.AspNet.WebPages bundles WebPages/Razor/Deployment and consumes Microsoft.AspNet.Razor. Layouts, RenderPage, helpers, functions, start pages, UrlData, extensionless/default pages and dynamic models work; file casing folds. Underscore files answer 404 and disabled folders 403; form reads trigger request validation. Version header/assembly identity remains 3.0.0.0. Dependency inspection and installer-path tooling refuse secondary-AppDomain/registry dependencies; Html.Hidden excludes LINQ-to-SQL Binary. File edits require process replacement. Helpers, WebMatrix.Data and WebMatrix.WebData are absent. |
| ASP.NET MVC 5 (`Microsoft.AspNet.Mvc`) | Supported | Rehost.AspNet.Mvc replaces System.Web.Mvc and depends on Rehost.AspNet.WebPages; assembly version 5.3.0.0, `X-AspNetMvc-Version: 5.3`. Controllers, areas, Razor views and layouts, `Views/Web.config` as the template ships it, MVC's 404 for an unknown controller, the error page and child-action output caching work; a `.cshtml` outside `Views` answers 403 as under disabled Web Pages. `System.Data.Linq.Binary` binds and renders in hidden fields when any LINQ to SQL implementation (for example Mindbox.Data.Linq) supplies a type by that name; object templates skip `System.Data.EntityState` by name too. Microsoft.Web.Mvc (Futures), Microsoft.AspNet.WebHelpers and WebMatrix.* are not shipped. Framework binaries compiled against System.Web.Mvc, such as Autofac.Mvc5, need recompiling against Rehost.Web.Mvc; [eShopLegacyMVC](../../apps/eShopLegacyMVC/DEVELOPMENT.md) runs with a recompiled Autofac.Mvc5. |
| Reflective write to a `readonly` static | Partial | Modern .NET refuses `FieldInfo.SetValue` on an initialized `static readonly` field with `FieldAccessException`, where Framework allowed it. The Web API host drops `readonly` from `HttpControllerRouteHandler._instance`, the one field the session route-handler recipe writes; `System.Web` statics and application code are unchanged, so any other such write fails as it does on modern .NET |
| Optimization/WebForms and WebGrease | Partial | Debug expansion and production combination/minification work for script and style bundles, including Bundle.config. Bundle caching, VaryBy breadth and WebGrease image spriting remain unassessed. |
| `Microsoft.Web.Infrastructure` API | Partial | The runtime bundle supplies four classes/seven methods under original namespaces. They forward module registration, dynamic validation, unload, CodeDOM extension checks and null-context execution to System.Web. No upstream implementation is imported. JScript/C++ extensions answer false because their providers are absent. Keeping the original package causes ambiguous-type compilation errors. |

## Requests, pages, and responses

| Capability | State | Boundary |
| --- | --- | --- |
| HTTP/1.1 request bodies | Supported | Fixed-length/chunked, sync/APM reads, buffered/bufferless input, async preload, abort, drain, and independent host/System.Web size limits |
| HTTP/2 | Supported | The request-body surfaces run over cleartext HTTP/2; System.Web sees its usual HTTP/1.1-shaped request |
| `Response.PushPromise` | Partial | The path is validated and nothing is pushed: the integrated-only call refuses itself and the imported `catch` swallows the refusal, so the caller sees no error. With page tracing on, the trace carries "Push promise is not supported" and the refusal. Framework itself documents the call as fire-and-forget that the server may ignore entirely |
| HTTP/3 | Unassessed | No transport gate |
| Client certificates | Unsupported | `Request.ClientCertificate` reports not present; behind a TLS-terminating proxy Kestrel never sees one, and forwarded-certificate translation into `CERT_*` is the recorded design when a consumer needs it |
| WebSockets (`IsWebSocketRequest`, `AcceptWebSocketRequest`, `AspNetWebSocket`) | Supported | Handshake, subprotocol, same-origin, closes and slim callback context match IIS. Post-accept body is dropped; callback `User` is null instead of IIS's anonymous principal |
| Mid-request `Response.Flush` / `FlushAsync` | Supported | Head and buffered bytes reach the client at each flush as on IIS (System.Web's own chunked framing over HTTP/1.1); late head changes, `End` after a flush, and errors after a flush preserve the Framework contract |
| `TransmitFile`/`WriteFile` over 2 GB | Supported | `SupportsLongTransmitFile` is on; the native-handle overload is unsupported |
| Forms, postback, view state, control state | Supported | URL-encoded and multipart parsing, event ordering, MAC enforcement, event validation, and request validation |
| Uploaded-file and raw-request `SaveAs` | Supported | Memory/disk-spill paths; Windows-rooted paths fail actionably off Windows rather than being misinterpreted |
| `Request.Filter` and raw-header grouping parity | Unassessed | No filter scenario; `HttpRequest.SaveAs` header grouping is not compared to IIS |
| Request/response cookies | Supported | Subkeys, defaults, validation, repeated `Set-Cookie`, attributes, mutation, and UTF-8 default response-header bytes |
| `Response.Headers` read/`Add`/`Set`/`Remove` off IIS | Supported | Managed writes form the store. Generated content/cache/redirect fields win; cookies append. After flush Add throws, Remove is inert. No IIS Server header; post-flush view is the host's single generated block |
| Request- and response-header byte encodings | Supported | Request-header bytes decode as IIS did (UTF-8, Latin-1 fallback, never 400); response headers leave in `<globalization responseHeaderEncoding>` (UTF-8 default; `iso-8859-1` exercised), read once the application has activated |
| `aspnet:MaxHttpCollectionKeys` | Supported | Opt-in: absent by default as on Framework 4.8.1; when configured it caps query, URL-encoded, multipart-field, and posted-file collections |
| Kestrel and `httpRuntime.maxRequestLength` limits | Supported | Each owner keeps its limit and error path; the smaller effective limit wins; legacy `system.webServer` limit translation is unassessed. The System.Web refusal answers as integrated did: 500 with `Content-Length`, no `Connection` header, and the connection stays open for the next request |
| Async pages, async module events, custom async handlers | Supported | Task-friendly synchronization context only; expected `HttpContext.Current` restoration is exercised |
| Page async timeout | Partial | TAP timeout/token behavior is exercised; a never-completing APM task remains pending, as on Framework |
| `PageAsyncTask` parallel/timeout handlers | Unsupported | Framework refuses them under the supported task-friendly context; the advertised legacy-context switch is also unsupported |
| `aspnet:UseTaskFriendlySynchronizationContext=false` | Unsupported | Activation fails naming the setting and required change |
| Illogical `CallContext` isolation | Supported with a boundary | Framework-exact for every System.Web path; a same-scope capture landing on its origin thread while data is still set is visible, unreachable through System.Web; net481-vs-port contract suite; see [call-context rationale](call-context-compatibility.md) |
| Application access to remoting `CallContext` | Unsupported | Compatibility type remains internal; publishing it would claim general remoting support |
| `customErrors` redirects | Partial | With `mode="On"`, an `<error statusCode="404">` row redirects to its authored URL and the application's own error page renders from the query string, including its `Request.IsLocal` detail panel, on all three platforms (Wingtip Toys). `defaultRedirect` for an unhandled exception, `Application_Error` reached before it, and `RemoteOnly` are unassessed. A query-bearing defaultRedirect lacks the aspxerrorpath loop marker and can recurse indefinitely; applications must avoid that shape. Native 404s bypass customErrors |
| `Response.End`, terminating redirects, `CompleteRequest` | Partial | Response/pipeline effects match, including a catch that wraps the termination or throws another exception in its place: the request still ends as the termination, with no `Application_Error`, and an ending `Response.Redirect` in a Web Pages page answers its 302. Named catch/abort differences are below |
| `catch (ThreadAbortException)` around termination | Partial | Never executes because modern .NET has no compatible thread-abort signal |
| `catch (Exception)` swallowing termination | Partial | Status and pipeline events match, but the response is sealed at `End`: what the catch writes is dropped, where Framework sent it. Code after the catch, which Framework never ran, runs until the pipeline step ends; its output is dropped and an exception it throws counts as the termination |
| `executionTimeout` | Partial | Cooperative delivery occurs between steps; an executing step is not interrupted and a never-returning step is not stopped |
| `Server.Transfer` and `Server.Execute` | Supported | Child execution, query/form semantics, writer capture, previous-page state, and static-file child are exercised |
| `Server.TransferRequest` | Unsupported | No integrated pipeline to re-enter; failure names `Transfer`/`Execute` alternatives |
| Static files through System.Web | Partial | IIS-derived extension/type map, hidden segments, normal ranges, HEAD, validators, 304, and sendfile-backed commit are exercised; `If-Range` is unassessed. Without a `caching` profile a static response carries no `Cache-Control` and no `Expires` on 200, 206, 304 and HEAD, as IIS's native module sent none. A missing file is a native 404: no `Application_Error`, no `customErrors`, `LogRequest` onward see the status |
| Path-taking APIs: includes, masters, site map, data/mail/control files, response files, `MapPath` | Supported | Framework path classification and case folding, including above-root includes. No portable spelling for absolute Windows physical paths; use virtual paths. Jet/OLEDB `AccessDataSource` excluded |
| Friendly URLs and application routing | Partial | Extensionless pages/handlers, segments, physical redirects, route ordering, mobile selection/switching, and direct/routed authorization are exercised; route escaping breadth and real upstream rewrite variables remain open |
| Response compression, HTTP/3 | Unassessed | Compression is IIS's own module ([IIS-role follow-up](follow-ups/iis-role-behaviors.md)); HTTP/3 has no transport gate. Client-visible streaming and WebSockets are now Supported |

## Configuration and IIS-derived behavior

| Capability | State | Boundary |
| --- | --- | --- |
| Framework-derived machine/root web configuration | Supported | Versioned assets default under `AppContext.BaseDirectory/configs` and may be overridden explicitly; application `web.config` is optional |
| App-root `system.webServer/staticContent` | Partial | MIME add/remove/clear and duplicate validation work. clientCache joins profile policy, custom text and max-age or no-cache into one comma-separated Cache-Control on 200/HEAD/206/304; empty composition emits nothing. UseExpires emits the configured Expires verbatim. Managed responses keep their own policies. Root-only; lower scopes, setEtag=false, invalid modes/spans and CR/LF values fail activation. ETag removal requires changing the managed static handler. |
| App-root `requestFiltering/hiddenSegments` | Supported | Case-insensitive add/remove/clear block exact hidden segments at any depth, including bin, App_* and web.config; similar names remain admissible. Refusals answer 404 without IIS's native wire substatus. |
| App-root `requestFiltering/fileExtensions` | Partial | IIS deny-list and application `add`/`remove`/`clear`/`allowUnlisted` semantics are supported; denials return 404 and invalid entries fail activation. The section is root-only, while IIS resolves it per path |
| URL canonicalization, path-info, `Request.RawUrl` | Supported | Slashes, encoded separators, dot segments, above-root 403, handler path-info split and canonical path plus verbatim query follow the adapter contract. Static wire-status differences remain in [IIS roles](follow-ups/iis-role-behaviors.md). |
| Per-folder `system.webServer/handlers` | Supported | Each folder `Web.config` merges into an immutable effective list at activation; mapping, path-info, and `managedHandler` use the deepest configured list. Multi-level compositions follow the tested merge algorithm but are not individually measured against IIS |
| Per-folder `system.webServer`, other sections | Refused | `<modules>` in a folder file is inert, which is IIS's own behavior — it ignores a subfolder section outright, silently — and `<validation>` decides the folder's classic-section waiver. Every other element there fails activation naming the file and the element: `staticContent`, `defaultDocument`, `requestFiltering`, `httpErrors`, `httpProtocol`, `rewrite` and the rest are read from the application root alone, where IIS honored several of them per folder |
| App-root `system.webServer/defaultDocument` | Supported | Directory requests rewrite to the first existing candidate in list order (app observes the list's casing), 301 slash redirect, 403-class refusal, and `enabled="false"` narrows to directory requests alone; the refusal's body is whatever `httpErrors` says for the client |
| App-root `system.webServer/caching` | Partial | Profiles set the static `Cache-Control` word by `location` (`Client`/`ServerAndClient` private, `Any`/`Downstream` public, `Server`/`None` no-cache) and nothing else: `duration`, `varyByHeaders`, `varyByQueryString` and `kernelCachePolicy` are read and dropped, and `enabled="false"` does not silence the word. IIS also stored the response and served later requests from it; this host runs every request, so a profile on a managed extension is not honored and preflight warns once (event 11). Per-folder files are unassessed, like the other static sections |
| App-root `system.webServer/httpProtocol/customHeaders` | Partial | Stamp every host response at head commit, including middleware errors, rewrite answers and WebSocket 101; managed removal cannot remove configured rows. X-Powered-By is inherited and removable. Cache-Control/Content-Type coalesce with commas; other duplicates use separate lines; empty values emit nothing. removeServerHeader controls Server; a customHeaders remove is inert. Root-only; duplicate names, invalid tokens and CR/LF fail activation. Values follow responseHeaderEncoding, unlike IIS's fixed Latin-1. |
| App-root `security/requestFiltering` limits | Partial | Declared Content-Length above maxAllowedContentLength answers 413 with Connection: close before the pipeline; chunked bodies bypass this check. The application limit configures Kestrel at startup; a lower host override still applies. Managed maxRequestLength retains its own 500. maxUrl counts the claimed script path's bytes, excluding path info; maxQueryString counts raw query bytes. Verbs are case-sensitive and denied values answer 404 before managed events or rewrite. Root-only; header/character/sequence/filter-rule settings remain refused. Native segment/URL caps have no equivalent; Kestrel limits and earlier managed path validation may reject first. |
| `<system.net>` in `web.config` | Unsupported | Declared as an ignored section so the application activates; nothing on .NET reads any of it, which preflight reports once as an error naming the file |
| `<system.data><DbProviderFactories>` | Partial | .NET's `DbProviderFactories` reads no configuration, so activation registers each application-root row with `RegisterFactory`; `GetFactory` and `SqlDataSource`'s `ProviderName` then find it. `System.Data.SqlClient` is built in and a row cannot replace it, as on Framework; `<remove>` and `<clear>` reach only configured rows. A name the host registered before activation keeps the host's factory. A broken row refuses activation naming the file and line, where Framework failed the first provider lookup and every one after it. Boundaries: Odbc, OleDb and OracleClient are not built in, so a row may claim those names; a folder `web.config` or `<location>` row is ignored, where Framework honored whichever path looked a provider up first; an exact duplicate row is accepted; `GetFactoryClasses` returns empty `Name` and `Description`, and an unloadable `type` fails `GetFactory` with `ArgumentException`, not `ConfigurationErrorsException` |
| Static `System.Configuration.ConfigurationManager` inside the application | Supported | Activation installs site `web.config` as process configuration, so app settings, connections and custom sections work for libraries such as Katana/EF; available |
| Broken `system.webServer` sections | Supported | Any honored section that fails to parse or validate refuses activation, naming the file and the entry; IIS instead scoped its 500.19 to the requests reading the section, so an application it served despite a latent duplicate must be corrected before it starts here |
| App-root `system.webServer/httpErrors` | Partial | At head commit, replacement retains status/headers and changes body, Content-Type and Content-Length; later writes after a flush continue. DetailedLocalOnly/Custom/Detailed choose detailed output, replacing only an empty entity. Auto honors TrySkipIisCustomErrors; PassThrough retains even an empty body; Replace overrides both. File rows use MIME mapping (unknown-extension fallback unassessed); missing files use built-in text. Redirect answers absolute 302 with Object Moved. Rows key by status/substatus, but only wildcard substatus matches because no native substatus is carried. Root-only: lower scopes, duplicate keys, ExecuteURL, defaultPath, allowAbsolutePathsWhenDelegated, absolute/outside-root files and invalid redirect targets fail activation. Default/detailed bodies are substitutes for IIS assets. Early middleware/rewrite responses bypass spool replacement. |
| `system.webServer/handlers` and `/modules` | Supported | Integrated merged lists replace classic sections: ordering, mutations, conditions, lazy handlers, native bridges and folder handlers. Boundaries: verb statuses, TransferRequest, some global/pre-send conditioning, and earlier activation failures |
| Shipped baseline `<modules>` and `<handlers>` | Supported | `applicationHost.config` carries managed modules/order and handler rows; classic defaults are retired. Native bridge makes StaticFile/protocol rows composable. Windows/FileAuthorization registrations are inert; registration is not a feature claim |
| `HttpRuntime.UsingIntegratedPipeline` / `IISVersion` | Supported | true and 10.0 select integrated feature branches; the internal engine stays classic ([ADR](adr/0013-integrated-pipeline-identity.md)). Native-only operations still refuse; optional WebSocket/abort seams require a capable host. |
| `MapRequestHandler`, `LogRequest`, `PostLogRequest` | Supported | Raised as classic execution steps where integrated raises them: `MapRequestHandler` straight after handler mapping and before `PostMapRequestHandler`, `LogRequest`/`PostLogRequest` after `PostUpdateRequestCache` and before `EndRequest`. Both Log events also fire after every early end — `Response.End`, `CompleteRequest`, a redirect, an unhandled exception, from a page or from `BeginRequest`. The response is open and buffered at all three, so writes, `AppendHeader` and `Flush` behave as in a page. Sync `+=` and the `AddOn*Async` overloads both work, and a `Global.asax` handler naming an event whose subscription is refused now fails the application instead of being dropped silently. `Response.StatusCode` at `LogRequest` after an unhandled error reads 500, as it did on integrated, because rendering occurs at the early-end jump |
| `HttpContext.RemapHandler` | Supported | Honored by handler mapping when called before the map step, as routing needs; called at or after it, the same `InvalidOperationException` integrated raises names `HttpApplication.MapRequestHandler` rather than storing a value nobody reads. A child `Server.Execute` runs inside the handler step, so a call from there is refused too |
| `HttpContext.CurrentNotification` / `IsPostNotification` | Supported with a boundary | The pair every managed event reports on an integrated pool, answered from the classic step list: `BeginRequest`; `AuthenticateRequest` for the authenticate pair; `AuthorizeRequest`, `ResolveRequestCache`, `MapRequestHandler`, `AcquireRequestState`, `ReleaseRequestState`, `UpdateRequestCache` and `LogRequest` for theirs, with `Post*` reporting the post phase of the base notification; `PreExecuteRequestHandler` at `PreRequestHandlerExecute`; `ExecuteRequestHandler` in the handler body and at `PostRequestHandlerExecute`; `EndRequest`; `SendResponse` in both pre-send events. `RequestCompleted` reads `EndRequest` and a module's `Init` on a request instance reads `BeginRequest`. Boundaries: where Framework throws `NullReferenceException` the port raises `InvalidOperationException` naming the boundary; the classic-only `DefaultAuthentication` step has no reading and inherits `AuthenticateRequest` |
| Writable `Request.Headers` | Supported with a boundary | The collection is the store, as it was under integrated: `Set` replaces, `Add` appends comma-joined, `Remove` deletes, `Clear` still throws `NotSupportedException`, and every mutation invalidates `Request.Params`. Mirrors follow Framework's own laziness: `ServerVariables["HTTP_*"]` only if that collection already existed at mutation time, `Request.Url` only if `Url` had not been read yet, and then with the host name only — the local port wins even when the rewrite names one. Boundaries: typed accessors (`Request.UserAgent`, `ContentType`) keep reading the worker request and do not follow, as on integrated; nor do the six server variables `GetSimpleServerVar` answers without populating the collection, `HTTP_USER_AGENT` among them; a `Remove` made while that collection exists but is unpopulated is lost to population while a `Set` survives it, as measured |
| `HttpApplication.OnExecuteRequestStep` | Supported | The step invoker both step managers already honored is reachable: a module registers a wrapper from `Init` and it runs around every step of the classic list. A call after `InitInternal` raises Framework's `OnExecuteRequestStep_Cannot_Be_Called` |
| `Response.AddOnSendingHeaders` | Supported | Callbacks fire at the head-commit point — after the `PreSendRequestHeaders` handlers and before status and headers are generated — with the status still what the application set, so a callback's `AppendHeader` or `StatusCode` change reaches the wire. Registration after the head has left still raises `HttpException` |
| `PreSendRequestHeaders` / `PreSendRequestContent` context | Supported | `HttpContext.Current` is set inside both events, as on integrated; classic left it null because the final flush can run after the thread context is detached |
| Late `HttpApplication` event binding | Refused | A `+=` after module initialization raises `InvalidOperationException` with Framework's own "Event handlers can only be bound to HttpApplication events during IHttpModule initialization." Classic accepted the binding and never ran the handler. A `-=` after initialization meets the same refusal, from a request or from a module's `Dispose` at unload, where `DisposeInternal` swallows it and `Application_End` still runs |
| Error page timing after an unhandled error | Supported | Application_Error runs first; ClearError suppresses rendering. Otherwise the early-end jump closes the response filter and renders a complete 500 before LogRequest/PostLogRequest/EndRequest, which may append or clear output. Later errors do not rerender an already-reported runtime error; final-flush/reporting failures emit swallowed-exception diagnostics. |
| `HttpContext.Current.Request` / `.Response` during application and module init | Supported | Hidden — `HttpException` "Request is not available in this context" / "Response is not available in this context." — inside `Application_Start`, the application's own `Init()` override and module `Init`, as integrated hid them and classic did not. `Server.MapPath` still works there, as Framework's own unhiding provides. `Application_End` and `Session_End` carry no context and are unaffected. The native initial-application case has no counterpart here: the port's first application instance initialises no modules, so nothing sees integrated's synthetic `/` request |
| `ServerVariables["WEBSOCKET_VERSION"]` | Supported | Answers `13` from the server-variable shortcut while `AllKeys` omits it and `Count` stays 45, which is the shape integrated reported. Katana's capability probe reads exactly this name and no longer withdraws the advertised WebSocket capability on the first request |
| `Response.ClientDisconnectedToken` | Supported with a boundary | Kestrel's `RequestAborted`: `CanBeCanceled` for the whole request and still readable from `HttpContext.AddOnRequestCompleted`, as integrated reported. Boundary: the port signals on FIN or RST, where IIS learned of the disconnect only when the server next touched the connection, so an idle request there was never signalled — code that relied on the token staying quiet sees it trip earlier here. OWIN now depends on this: Katana's `DisconnectWatcher` uses this token directly, with no polling fallback, so a host whose worker request leaves the disconnect seam unimplemented raises `PlatformNotSupportedException` into every OWIN request |
| `Request.Abort` | Supported with a boundary | Resets the client connection without ending the request: the call returns, the handler runs on, `Response.IsClientConnected` goes false and the client sees a forcible reset. Boundary: the flush after the abort returns without raising, where integrated raised `HttpException: The remote host closed the connection.` — Kestrel discards a write to an aborted connection instead of failing it, and the classic flush path additionally skips the send once `IsClientConnected` has latched the disconnect |
| `Response.SubStatusCode` | Supported with a boundary | Defaults to `0`, round-trips, and never reaches the wire — a response with a substatus set is byte-identical to one without, as on integrated. Setting `StatusCode` still resets it, and setting either after the headers have gone still raises `HttpException`. Boundary: IIS consumed the value in its log and the port has no log, so nothing reads it back |
| `Request.InsertEntityBody` | Supported | Both overloads return with no effect on the request or response, which is what the integrated call did with no native handler behind it. Framework's own checks stay and run in Framework's own order: the WebSocket-transition guard on the three-argument overload, then `ArgumentNullException`, `ArgumentOutOfRangeException` and `ArgumentException` |
| `HostingEnvironment.StopListening` | Supported | The host's stopping notification raises the event and calls `IStopListeningRegisteredObject.StopListening` before the registered objects are stopped, which is the order an integrated pool stop produced; an application-requested recycle raises neither, as on both IIS pools. Katana's `ShutdownDetector` binds the event by reflection, so `OwinApplication.ShutdownToken` now cancels at the stop rather than only at `IRegisteredObject.Stop`. Boundaries: IIS put about a second between the signal and `Stop`, and the port raises them back to back; a subscriber that throws ends the raise for later subscribers, as Framework's unguarded multicast did, and the host swallows the throw into the runtime event source so teardown still completes |
| `Context.User` timing at `AuthenticateRequest` | Supported | Under `authentication mode` `None` and `Forms` the port matches both IIS pools exactly — `null` at `AuthenticateRequest`, a `GenericIdentity` at `PostAuthenticateRequest` — because the classic `DefaultAuthentication` step sits between the two events. The integrated-versus-classic difference exists only under `mode="Windows"`, which fails activation here. `HttpApplication.DefaultAuthentication` is an internal event, so an `Application_DefaultAuthentication` method never fires on any pool |
| Native handler-execution and URL denial | Refused | security/authorization fails activation regardless of contents, and handlers accessPolicy fails unless it grants exactly Read, Write, Script and Execute (any order, spacing or case), which denies nothing; both at root, folder or location scope. Diagnostics name file, element and location and suggest system.web/authorization, which covers managed content only unless all-request module execution is enabled. Native per-path enforcement over static content remains [open](follow-ups/iis-integration-plan.md). |
| `HostingEnvironment.MaxConcurrentRequestsPerCPU` / `MaxConcurrentThreadsPerCPU` | Unsupported | Both accessors refuse with PlatformNotSupportedException naming the property and directing concurrency configuration to the host; no IIS application-pool throttles exist. |
| `DefaultAuthenticationModule.Authenticate` | Unsupported | The subscription is refused with Framework's own integrated message naming `DefaultAuthentication.Authenticate`, which is what a migrating application's integrated pool said, even though the classic `DefaultAuthentication` step it fired from does exist here. A `Global.asax` `DefaultAuthentication_Authenticate` method therefore fails the application at init rather than being dropped. The module's own hook position and anonymous principal are unchanged |
| `DefaultHttpHandler` | Unsupported | `BeginProcessRequest` refuses with Framework's own integrated message naming it; there is no IIS to hand the request back to. The refusal sits ahead of the type's other public members (`OnExecuteUrlPreconditionFailure`, `OverrideExecuteUrlPath`, `EndProcessRequest`, `IsReusable`), so an application subclass named in a `<handlers>` row fails on that URL's first request, as integrated IIS made it fail, unless the subclass overrides `BeginProcessRequest` itself. The baseline's native `StaticFile` row uses an internal `StaticFileBridgeHandler` subclass, so static content is unaffected. The subclass keeps deriving from `DefaultHttpHandler` because `ImplicitAsyncPreloadModule` and `Server.Execute` type-test for it |
| `system.webServer/rewrite` (IIS URL Rewrite Module) | Partial | Inbound rules from the application root `web.config` run before the managed pipeline, where the native module ran them: on the canonical URL, after the original URL has faced request filtering and with the rewritten one filtered again, so a rule reaches nothing a request could not. `RawUrl` stays what the client asked for and every other path member follows the rewritten URL, which is what carries form actions, client-relative hrefs, relative `Response.Redirect`, `customErrors`, Friendly URLs and the output cache with no further work. `IIS_WasUrlRewritten`, `REQUEST_URI`, `UNENCODED_URL`, `CACHE_URL` and an overwritten `X-Original-URL` answer, out of `ServerVariables.AllKeys` as on IIS. The port owns the answers `Microsoft.AspNetCore.Rewrite` gets wrong: the rule's query before the request's, an absolute `Location` with IIS's reason phrase and `Object Moved` body, IIS's stock error body for a custom response, and a reset connection for `AbortRequest`. Boundaries refused at activation: outbound rules, `<serverVariables>`, `<globalRules>`, wildcard patterns, `subStatusCode`, duplicate rule names, a `<rewrite>` section below the application root or inside `<location>`, a `Rewrite` target that leaves the application, and any server variable outside the parser's list of 17. Accepted and named: patterns see the re-encoded path (`%20`, `%C3%A9`) where IIS matched the decoded one, a condition's `REQUEST_URI` carries no query, `HTTPS` reads upper case, `trackAllCaptures` numbering differs, `IsFile` also matches a directory, and the original request's second `LogRequest`/`EndRequest` tail is not reproduced, so the managed pipeline runs once, on the rewritten URL |
| Unhonored `system.webServer` sections | Refused | `<system.webServer>` is honored in the application root alone, and an element with no reader there fails activation naming the file and the element's path under the section, rather than running as if the application had never configured it. The names an application can set that this refuses: `directoryBrowse`, `httpRedirect`, `applicationInitialization`, `httpProtocol/redirectHeaders`, `tracing/traceFailedRequests`; `urlCompression` and `httpCompression` warn once instead (event 12, row below). The 23 sections IIS locks in its own `applicationHost.config` are not application-settable there either, so they never reach this list. Any `<system.webServer>` inside a `<location>` block fails activation whatever it holds, since nothing here reads it and IIS applied it to that path; `<system.web>` inside `<location>` is untouched, the Framework's own configuration system honoring it as before |
| Static and dynamic response compression | Unsupported | The host performs no compression. urlCompression/httpCompression warn once at activation. Configure ASP.NET Core Response Compression before UseRehostWeb; static/TransmitFile interaction remains unassessed. |
| Memory monitoring | Partial | GC-derived pressure and WorkingSet replace native physical/private-byte readings. Nonzero cache privateBytesLimit is refused because retained graph size is unavailable. Collection decommits through blocking compacting GC; repeated callback failures stop the monitor after diagnostics. Container pressure/reclamation remains [unassessed](follow-ups/container-memory-validation.md). |
| Configuration reload | Partial | Configuration is immutable for the generation, but file changes are not watched or diagnosed; operators must replace the process explicitly |
