# Common Web Forms feature gaps, ranked

Snapshot: `dd92948ce341e815c42efe2ec30778cb348c2313` (2026-08-21).

## Scope and method

This ranks application-visible ASP.NET Web Forms features that are absent or
materially limited in the portable port. It is **an inference, not telemetry**:
there is no authoritative census of deployed Web Forms applications. Ordering
combines (1) presence in Microsoft defaults, templates, documentation, package
downloads, or representative application source; (2) likelihood of blocking an
unchanged application; and (3) severity of the current boundary. A feature used
by many applications but already working is not a gap.

The repository's compatibility map is the support authority. Source/tests were
used to distinguish a real gap from documentation lag. “Unassessed” means no
support claim, not proof that every path fails.

## Ranking

| Rank | Feature | Current gap | Prevalence/impact signal |
| ---: | --- | --- | --- |
| **1** | Classic Forms Authentication, Membership, Roles, Profile, anonymous identity | Compiled APIs exist, but the whole feature is unassessed and its modules/providers are not gated; the shipped default module list omits `FormsAuthenticationModule`, `RoleManagerModule`, `ProfileModule`, and `AnonymousIdentificationModule` ([map](https://github.com/exfinder/rehost-webforms/blob/dd92948ce341e815c42efe2ec30778cb348c2313/docs/compatibility.md#L143-L149), [baseline](https://github.com/exfinder/rehost-webforms/blob/dd92948ce341e815c42efe2ec30778cb348c2313/src/Rehost.WebForms.Runtime/configs/rehost-webforms.web.config#L184-L189)). OWIN cookie authentication is a working alternative, not compatibility for these APIs. | Microsoft's Web Forms migration guide says the universal membership provider and optional role provider are **commonly deployed**, and that most applications use membership, often with roles. IIS's pipeline inventory also includes Forms Authentication, Profile, Role Manager, and Anonymous Identification modules ([migration guide](https://learn.microsoft.com/en-us/dotnet/architecture/blazor-for-web-forms-developers/security-authentication-authorization), [IIS architecture](https://learn.microsoft.com/en-us/iis/get-started/introduction-to-iis/introduction-to-iis-architecture)). Authentication failure blocks principal user journeys, hence #1. |
| **2** | Integrated-only `system.webServer` module and handler mappings | Classic `system.web/httpModules` registration remains available. The gap is narrower: `system.webServer/modules` and `/handlers` are not translated, so an extension registered only there is ignored; omitted handler fallbacks can also fail silently ([map](https://github.com/exfinder/rehost-webforms/blob/dd92948ce341e815c42efe2ec30778cb348c2313/docs/compatibility.md#L118-L126)). | Microsoft calls modules/handlers integral to ASP.NET. The representative eShop app shows the common dual-registration shape: Autofac and Application Insights entries occur in both classic and integrated sections, while its async session replacement is integrated-only ([official explanation](https://learn.microsoft.com/en-us/troubleshoot/developer/webapps/aspnet/development/http-modules-handlers), [classic entries](https://github.com/dotnet-architecture/eShopModernizing/blob/63bc9ec4414d7e281dc9f9d7bdcf70030950457d/eShopLegacyWebFormsSolution/src/eShopLegacyWebForms/Web.config#L38-L43), [integrated entries](https://github.com/dotnet-architecture/eShopModernizing/blob/63bc9ec4414d7e281dc9f9d7bdcf70030950457d/eShopLegacyWebFormsSolution/src/eShopLegacyWebForms/Web.config#L70-L81)). Its duplicated classic entries may suffice here; eShop is evidence of configuration shape, not proof this gap blocks that app. |
| **3** | Production session state: SQL Server/State Server, expiry events, cookieless IDs | `InProc` and custom providers work. `SQLServer` is not implemented; native `StateServer` is explicitly unsupported; `Session_End` on expiry and cookieless modes remain unassessed ([map](https://github.com/exfinder/rehost-webforms/blob/dd92948ce341e815c42efe2ec30778cb348c2313/docs/compatibility.md#L137-L146)). | Session is enabled by default in ASP.NET and Microsoft's docs identify SQL Server/State Server as the web-farm stores ([session overview](https://learn.microsoft.com/en-us/previous-versions/aspnet/ms178581%28v%3Dvs.100%29), [SQL setup](https://learn.microsoft.com/en-us/troubleshoot/developer/webapps/aspnet/development/configure-sql-store-session-state)). eShop stores request-visible values in Session ([source](https://github.com/dotnet-architecture/eShopModernizing/blob/63bc9ec4414d7e281dc9f9d7bdcf70030950457d/eShopLegacyWebFormsSolution/src/eShopLegacyWebForms/Global.asax.cs#L38-L45)). The gap mainly hits restart/farm-safe deployment, not a single-process app. |
| **4** | Default machine-key continuity across restart and scale-out | Literal `<machineKey>` values interoperate for the exercised page. Auto-generated keys are process-scoped, so auth cookies and protected state die on restart and cannot span instances; isolation suffixes/rotation remain open ([map](https://github.com/exfinder/rehost-webforms/blob/dd92948ce341e815c42efe2ec30778cb348c2313/docs/compatibility.md#L137-L141), [current backlog](https://github.com/exfinder/rehost-webforms/blob/dd92948ce341e815c42efe2ec30778cb348c2313/docs/backlog.md#L38-L41)). | `machineKey` protects Forms Authentication and view state; Microsoft requires identical explicit keys across a farm ([MachineKeySection](https://learn.microsoft.com/en-us/iis/wmi-provider/machinekeysection-class), [view-state guidance](https://learn.microsoft.com/en-us/previous-versions/aspnet/bb386448%28v%3Dvs.100%29)). Explicit configuration is a viable workaround, so below session despite high impact. |
| **5** | Full-page output caching and general cache policy/provider behavior | Basic fragment caching works, but the general cache/output-cache surface is unassessed and `OutputCacheModule` is absent from the shipped default modules ([map](https://github.com/exfinder/rehost-webforms/blob/dd92948ce341e815c42efe2ec30778cb348c2313/docs/compatibility.md#L143-L150), [baseline](https://github.com/exfinder/rehost-webforms/blob/dd92948ce341e815c42efe2ec30778cb348c2313/src/Rehost.WebForms.Runtime/configs/rehost-webforms.web.config#L184-L189)). | Microsoft describes output caching, fragment caching, and the Cache API as the three established ASP.NET caching options and important for performance ([caching overview](https://learn.microsoft.com/en-us/aspnet/web-forms/overview/moving-to-aspnet-20/caching), [data-app tutorial](https://learn.microsoft.com/en-us/aspnet/web-forms/overview/data-access/caching-data/caching-data-with-the-objectdatasource-cs)). Usually a performance/scale blocker rather than a functional one. |
| **6** | Production bundling/minification (`System.Web.Optimization`/WebGrease) | Source compiles and debug bundle expansion works, but production combination, minification, caching, request handling, and cross-platform gates remain open ([map](https://github.com/exfinder/rehost-webforms/blob/dd92948ce341e815c42efe2ec30778cb348c2313/docs/compatibility.md#L62-L64), [backlog](https://github.com/exfinder/rehost-webforms/blob/dd92948ce341e815c42efe2ec30778cb348c2313/docs/backlog.md#L176-L179)). | Microsoft's eShop and both stock templates register bundles; eShop references both Optimization packages ([eShop startup](https://github.com/dotnet-architecture/eShopModernizing/blob/63bc9ec4414d7e281dc9f9d7bdcf70030950457d/eShopLegacyWebFormsSolution/src/eShopLegacyWebForms/Global.asax.cs#L29-L35), [packages](https://github.com/dotnet-architecture/eShopModernizing/blob/63bc9ec4414d7e281dc9f9d7bdcf70030950457d/eShopLegacyWebFormsSolution/src/eShopLegacyWebForms/packages.config#L19-L27)). NuGet reports **169.8M** downloads for the Microsoft Optimization package and **8.7M** for its Web Forms control as of the snapshot ([NuGet core](https://www.nuget.org/packages/Microsoft.AspNet.Web.Optimization), [NuGet Web Forms](https://www.nuget.org/packages/Microsoft.AspNet.Web.Optimization.WebForms)); downloads are only a prevalence signal, not application counts. |
| **7** | IIS application policy: nested configuration, request-filtering limits, custom headers, `httpErrors` | App-root static content, hidden segments, and default documents work. Per-folder `system.webServer`, request-filtering limits, custom headers, and `httpErrors` are unassessed; unhonored sections are silently ignored ([map](https://github.com/exfinder/rehost-webforms/blob/dd92948ce341e815c42efe2ec30778cb348c2313/docs/compatibility.md#L114-L127)). | Microsoft documents request filtering as IIS's built-in security feature, configured through application `Web.config`, and Web Forms guidance treats safe error handling as normal application behavior ([request filtering](https://learn.microsoft.com/en-us/iis/configuration/system.webServer/security/requestFiltering/), [Wingtip error handling](https://learn.microsoft.com/en-us/aspnet/web-forms/overview/getting-started/getting-started-with-aspnet-45-web-forms/aspnet-error-handling)). These often cause security/operations divergence rather than compile failure. |
| **8** | ReportViewer/RDLC pages | A production candidate's `.rdlc` build provider and `.axd` handler depend on a closed-source, GDI+-bound assembly; the port currently needs a named unsupported boundary, not silent fall-through ([backlog](https://github.com/exfinder/rehost-webforms/blob/dd92948ce341e815c42efe2ec30778cb348c2313/docs/backlog.md#L101-L106)). | Microsoft's Web Forms ReportViewer package reports **11.0M** downloads and explicitly supplies the ASP.NET Web Forms control ([NuGet](https://www.nuget.org/packages/Microsoft.ReportingServices.ReportViewerControl.WebForms)). This is a common ecosystem blocker, but likely requires substitution rather than a source port. |
| **9** | Legacy declarative data stack: `LinqDataSource`, `EntityDataSource`, Dynamic Data, typed DataSets | `System.Web.DynamicData` is not carried and its hook is inactive; Entity/Dynamic Data remain absent or unassessed; `.xsd` typed-DataSet generation fails explicitly ([map](https://github.com/exfinder/rehost-webforms/blob/dd92948ce341e815c42efe2ec30778cb348c2313/docs/compatibility.md#L56-L61)). | Microsoft presents Linq, Entity, Object, SQL, XML, and other data-source controls as the built-in declarative data model ([data-source overview](https://learn.microsoft.com/en-us/previous-versions/aspnet/ms227679%28v%3Dvs.100%29)). eShop references `System.Web.DynamicData` and `System.Web.Entity`, though that alone does not prove runtime use ([project](https://github.com/dotnet-architecture/eShopModernizing/blob/63bc9ec4414d7e281dc9f9d7bdcf70030950457d/eShopLegacyWebFormsSolution/src/eShopLegacyWebForms/eShopLegacyWebForms.csproj#L173-L185)). Modern apps using EF directly avoid much of this gap. |
| **10** | Visual Basic runtime page/App_Code compilation | C# is supported; configured VB compilation fails actionably ([map](https://github.com/exfinder/rehost-webforms/blob/dd92948ce341e815c42efe2ec30778cb348c2313/docs/compatibility.md#L45-L50), [provider registration](https://github.com/exfinder/rehost-webforms/blob/dd92948ce341e815c42efe2ec30778cb348c2313/src/Rehost.WebForms.Runtime/configs/rehost-webforms.web.config#L11-L24)). | Microsoft Web Forms material treats `.vb` and `.cs` code-behind as the two normal languages and publishes parallel VB/C# deployment guidance ([Microsoft chapter](https://learn.microsoft.com/en-us/previous-versions/aspnet/hh147281%28v%3Dvs.88%29), [VB deployment tutorial](https://learn.microsoft.com/en-us/aspnet/web-forms/overview/older-versions-getting-started/deploying-web-site-projects/determining-what-files-need-to-be-deployed-vb)). Prevalence relative to C# is unknown; severity is total for a VB Web Site, hence included but ranked last. |

## Not counted as current feature gaps

- **UpdatePanel/Timer/page methods/QueryExtender/built-in JSON app-service
  routing:** the compatibility map still says async postbacks are open, but
  current HEAD has Kestrel behavior tests for panel deltas, triggers, errors,
  redirects, Timer, page methods, QueryExtender, and app-service routing
  ([tests](https://github.com/exfinder/rehost-webforms/blob/dd92948ce341e815c42efe2ec30778cb348c2313/tests/Rehost.WebForms.Hosting.Tests/AjaxOverKestrelTests.cs#L69-L250)). This is support-map lag, not an actual missing implementation.
- **`ScriptResource.axd` release assets:** compatibility rows contradict each
  other, but current handler registration and tests prove release-script
  delivery ([registration](https://github.com/exfinder/rehost-webforms/blob/dd92948ce341e815c42efe2ec30778cb348c2313/src/Rehost.WebForms.Runtime/configs/rehost-webforms.web.config#L130-L139), [test](https://github.com/exfinder/rehost-webforms/blob/dd92948ce341e815c42efe2ec30778cb348c2313/tests/Rehost.WebForms.Hosting.Tests/AjaxOverKestrelTests.cs#L69-L79)). Debug scripts/localized satellites remain a narrower limitation.
- **Precompiled deployment and publish tooling:** materially incomplete
  ([map](https://github.com/exfinder/rehost-webforms/blob/dd92948ce341e815c42efe2ec30778cb348c2313/docs/compatibility.md#L58-L58)), but excluded from the ranking as deployment/build workflow rather than end-user application behavior. Microsoft still documents it as a normal Web Site deployment model ([precompilation](https://learn.microsoft.com/en-us/aspnet/web-forms/overview/older-versions-getting-started/deploying-web-site-projects/precompiling-your-website-cs)).

## Portable-contract exclusions

Do not interpret every Framework difference as unfinished port work. The project
intentionally excludes strong-name/binary interchangeability, native IIS
pipeline machinery/libraries, partial trust/CAS, COM+/Enterprise Services,
remote IIS administration, and Windows-only Access/Jet behavior
([project contract](https://github.com/exfinder/rehost-webforms/blob/dd92948ce341e815c42efe2ec30778cb348c2313/PROJECT.md#L29-L43), [map](https://github.com/exfinder/rehost-webforms/blob/dd92948ce341e815c42efe2ec30778cb348c2313/docs/compatibility.md#L24-L35), [boundaries](https://github.com/exfinder/rehost-webforms/blob/dd92948ce341e815c42efe2ec30778cb348c2313/docs/compatibility.md#L151-L154)). Native State Server and closed-source/GDI+-bound ReportViewer are therefore substitution/boundary problems; SQL session, module translation, classic auth, cache behavior, and persistent keys are portable gaps.
