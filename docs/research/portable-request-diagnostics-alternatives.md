# Portable request diagnostics: boundary alternatives

Research for [portable request diagnostics](../follow-ups/portable-request-diagnostics.md);
also serves [silent exception swallowing](../follow-ups/silent-exception-swallowing.md),
[portable runtime metrics](../follow-ups/portable-runtime-metrics.md), and
[Windows platform diagnostics](../follow-ups/windows-platform-diagnostics.md).
Question: what boundary should carry runtime diagnostics (startup, compilation,
request errors, swallowed exceptions) out of the ported runtime? Evaluated
against the proposal to hand the runtime the host's
`Microsoft.Extensions.Logging.ILogger`. The options survey below is the
original research; the [agreed design](#agreed-design) section records where
the subsequent design discussion landed and supersedes the original
recommendation.

## Diagnostic exit points today

On Framework, every sink below ends in `webengine4.dll`, the Windows Event
Log, WMI, or IIS ETW. In the port each is one of: replaced by
`WebFormsRuntimeEventSource`, inert by construction, or dropped by
configuration.

The port therefore already has a portable channel:
`src/Rehost.WebForms.Runtime/Compatibility/Diagnostics/WebFormsRuntimeEventSource.cs`,
an internal `EventSource` named `Rehost.WebForms.Runtime` with seven events
(unhandled exception, swallowed request exception, assembly resolution,
compilation failure, monitor sample failure/disable, auto-generated machine
key). New-authored code already writes to it (`MonitorFailurePolicy.cs`,
`GeneratedAssemblyLoader.cs`, `ApplicationConfigurationPreflight.cs`,
`RoslynCSharpCompiler.cs:187`). Consumers today attach an `EventListener`:
`tests/parity/src/Rehost.WebForms.Parity.Harness/RuntimeDiagnosticListener.cs`
and `tests/Rehost.WebForms.Runtime.Tests/Compatibility/Hosting/AutoGeneratedMachineKeyReportTests.cs`.

## Framework default delivery (golden-config evidence)

From the pinned 4.8.1 root configs in `third_party/microsoft/framework-config`:

- `healthMonitoring` is a machine-to-application section
  (`machine.config:92`); `enabled` defaults to `true`
  (`Configuration/HealthMonitoringSection.cs:254,336`).
- Root `web.config:130-167` registers three providers — `EventLogProvider`,
  `SqlWebEventProvider`, `WmiWebEventProvider` — and exactly two rules, both
  targeting `EventLogProvider`: **All Errors** (`WebBaseErrorEvent`, which
  `RaiseRuntimeError` feeds) and **Failure Audits** (`WebFailureAuditEvent`),
  each throttled to `minInterval="00:01:00"`.

So on Framework, a request error or failure audit lands in the Windows
Application event log by default; WMI and SQL delivery exist but have no
default rule. The exact event-log IDs and formatting are unmeasured here (no
winbox reading taken; the content comes from `Misc.FormatExceptionMessage`,
`Misc.cs:76-92`, which emits full messages and stack traces).

The port ships the section type (`configs/rehost-webforms.machine.config:24`)
but its root `rehost-webforms.web.config` carries no `healthMonitoring`
element: schema defaults leave monitoring enabled with zero providers and zero
rules, so every raised event is classified and discarded.
[Compatibility](../compatibility.md) already records "health modules are
absent" under unsupported Windows behavior.

## How modern .NET reports the same conditions

- **ASP.NET Core hosting uses both channels.** An unhandled request exception
  is logged through `ILogger` (category `Microsoft.AspNetCore.Hosting.Diagnostics`)
  *and* raised as `HostingEventSource.UnhandledException` (event 5,
  `Microsoft-AspNetCore-Hosting`), plus `DiagnosticListener` events for
  in-process consumers such as Application Insights.
  <https://github.com/dotnet/aspnetcore/blob/main/src/Hosting/Hosting/src/Internal/HostingEventSource.cs>,
  <https://github.com/dotnet/aspnetcore/blob/main/src/Hosting/Hosting/src/Internal/HostingApplication.cs>
- **Kestrel** logs connection/request errors through `ILogger` categories
  (`Microsoft.AspNetCore.Server.Kestrel[.BadRequests|.Connections|...]`),
  emits metrics through `KestrelEventSource` counters, and raises a
  `DiagnosticSource` event for requests rejected below the hosting layer.
  <https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/kestrel/diagnostics?view=aspnetcore-10.0>
- **The BCL networking stack is EventSource/Metrics/Activity only** — no
  `ILogger` anywhere in `System.Net.*`; `ILogger` output for `HttpClient`
  comes from the `IHttpClientFactory` layer above it.
  <https://learn.microsoft.com/en-us/dotnet/fundamentals/networking/telemetry/overview>
- **Official library-author guidance**: a library that takes a logger should
  accept `ILoggerFactory`, default to `NullLogger`, and use source-generated
  `LoggerMessage` methods; the abstractions package is the sanctioned
  dependency.
  <https://learn.microsoft.com/en-us/dotnet/core/extensions/logging/library-guidance>

The split in practice: components below the DI layer (BCL, Kestrel internals'
counters) use `EventSource`; components that live inside a generic-host
application and want operator-visible logs use `ILogger`; the flagship server
stack does both. This runtime sits exactly on that line — it is BCL-shaped
inside (static `HttpRuntime`, no DI) and host-adapter-delivered outside.

## Options

### 1. Inject `ILogger`/`ILoggerFactory` into the runtime (the proposed idea)

The host would pass a logger through `WebFormsApplicationOptions` at
`WebFormsApplication.Initialize`
(`src/Rehost.WebForms.Runtime/Compatibility/Hosting/WebFormsApplication.cs:39`),
the one existing intake seam.

- The runtime csproj today references no `Microsoft.Extensions.*` package
  (`src/Rehost.WebForms.Runtime/Rehost.WebForms.Runtime.csproj`); this adds
  its first, though `Microsoft.Extensions.Logging.Abstractions` is small and
  explicitly blessed for libraries.
- The deep call sites are static imported code (`Misc`, `HttpRuntime`,
  `WebEvents`). No constructor injection reaches them; the `ILogger` would be
  stored in a runtime-owned static anyway. The injection buys nothing
  structural — only the *type* at the boundary changes.
- It would either replace or duplicate `WebFormsRuntimeEventSource`, which is
  already committed behavior recorded in the ledger (P31) and consumed by the
  parity harness.
- With no logger supplied (tests, non-generic-host embedding), `NullLogger`
  silently discards — the same "vanish" problem, now without even
  `dotnet-trace` reachability.

### 2. EventSource only (status quo, extended)

Zero dependencies, matches the BCL precedent, near-zero cost with no listener
(one `IsEnabled` check per `WriteEvent`), reachable out-of-process via
EventPipe/`dotnet-trace`/`dotnet-monitor` without code.

But an `EventSource` nobody subscribes to is invisible in the place operators
actually look: the ASP.NET Core host's log pipeline. A first-request
compilation failure would appear on the rendered error page and nowhere in the
console/JSON/OTLP logs. That is the "events vanish silently" failure the
follow-up rules out, merely relocated.

### 3. EventSource in the runtime + host-adapter `EventListener`→`ILogger` bridge — original recommendation, superseded

Keep `WebFormsRuntimeEventSource` as the single in-runtime exit point.
`Rehost.WebForms.Hosting` — which already has `ILoggerFactory` via
`FrameworkReference Microsoft.AspNetCore.App` and `InternalsVisibleTo` access
to the runtime — installs an `EventListener` in `AddRehostWebForms` that
forwards every event to an `ILogger`. This is the ASP.NET Core dual-channel
shape with each half owned where it is cheap: the runtime stays
dependency-free and static-friendly; the adapter, which is the only supported
host, delivers to `ILogger` by default with zero consumer configuration.

Superseded because `EventSource` serializes every payload to manifest types
even for an in-process `EventListener`: the bridge only ever holds strings and
must call `ILogger` with `exception: null`. Sinks that treat the `Exception`
object specially (Application Insights exception telemetry, Sentry, providers
rendering the stack separately) degrade to a message-embedded string. The
design discussion made exception-object fidelity a requirement, which rules
this option out as the sole delivery path.

### 4. A runtime-owned `IRehostDiagnostics` interface

Invents a third abstraction next to the two the ecosystem already has. Every
call site still needs an ambient static to reach it, the public API grows
(against the small-API principle), and no tooling can subscribe to it. The
only thing it buys over option 3 — a typed seam for the adapter — the
`EventSource` already provides via event ids and payloads. Rejected.

A narrower variant surfaced during the design discussion: a single-method sink
(`void Event(int id, EventLevel level, string name, props, Exception?)`)
installed by the host and called from the `[NonEvent]` wrappers, keeping
`Microsoft.Extensions.*` out of the runtime while carrying live objects. Also
rejected once the dependency question was settled: the shape is
`ILogger.Log<TState>` re-invented, minus category filtering, `LoggerMessage`
source generation, and ecosystem familiarity. Its only remaining argument was
the zero-external-package property of the runtime csproj, which was judged not
worth owning a duplicate abstraction —
`Microsoft.Extensions.Logging.Abstractions` is netstandard, stable, blessed
for libraries, and already present transitively in every supported host.

### 5. Portable health-monitoring providers

Keeping `System.Web.Management` alive as *the* boundary fails on its own
mechanics: delivery is config-gated (any app config mistake silently disables
it), buffered and throttled (`bufferModes`, `minInterval`), per-application
rather than per-process, and its raise path swallows its own failures
(`WebEvents.cs:432`). It is a compatibility surface, not a diagnostics
foundation. Policy: the three Windows providers are unsupported (they can only
throw `DllNotFoundException`); the managed provider model (`Sql`, mail,
custom `WebEventProvider` subclasses) stays backlog until a real application
configures one, per the ported-when-reached rule.

## Agreed design

Settled in design discussion, 2026-08-30. Two requirements were added over the
original research: exception *objects* must reach `ILogger` intact (rules out
any path that stringifies at the boundary, including the option-3 bridge), and
`ILogger` must not *replace* the `EventSource` (no-host and broken-bootstrap
observability was the reason `EventSource` won, and that reason stands).

- **Dual channel, one choke point.** `WebFormsRuntimeEventSource` stays the
  single exit surface imported code sees. Each event kind gets a `[NonEvent]`
  overload taking the natural types (`Exception`, not `string`); the overload
  (a) calls a `[LoggerMessage]`-source-generated typed log method with the
  live `Exception` and (b) writes the string form via the `[Event]` method so
  EventPipe/`dotnet-trace` and the parity harness keep working with no host
  attached. Payload names survive `WriteEvent` (parameter names are the
  manifest schema); `EventLevel`/event id map mechanically to
  `LogLevel`/`EventId`. Adding an event kind touches one file; the two
  channels cannot drift because the wrapper is the only caller of both.
- **Existing signatures refactor to take exceptions as objects.** Three
  current call sites pre-stringify and reshape under the `[NonEvent]` face:
  `MonitorFailurePolicy.cs:29,36` (`e.ToString()` moves inside the wrapper);
  `Misc.ReportUnhandledException` (`Misc.cs:66` — wrapper takes
  `(Exception, string[])` and keeps calling `FormatExceptionMessage`
  internally, since that format is the Framework event-log content parity,
  while the raw exception rides to `ILogger`); and `HttpRuntime.cs:1844`,
  which folds two exceptions into one string. `ILogger` has one `Exception`
  slot, so the signature becomes
  `SwallowedException(string site, Exception swallowed, Exception? context)` —
  the swallowed reporting failure is the event's subject and takes the slot,
  the original request error becomes a named prop; the `[Event]` string form
  keeps both texts so EventPipe output loses nothing. Wrapping both in an
  `AggregateException` was rejected as misrepresenting what happened. Changing
  event 2's payload shape changes what listeners see: the parity harness
  (`RuntimeDiagnosticListener`) and the machine-key report test attach to this
  source, so the refactor updates them in the same change and notes it against
  ledger P31.
- **Runtime takes `Microsoft.Extensions.Logging.Abstractions`** — its first
  external package reference, accepted deliberately: the abstractions package
  is small, netstandard, sanctioned for libraries (library-guidance link
  above), and every supported host already carries it via
  `Microsoft.AspNetCore.App`. In exchange the runtime gets category-based
  filtering (`Logging:LogLevel:Rehost.WebForms`), `LoggerMessage` typing, and
  ambient enrichment for free.
- **`ILoggerFactory` is an explicit input on the existing intake seam**
  (`WebFormsApplicationOptions` at `WebFormsApplication.Initialize`), stored
  once in the diagnostics choke point, `NullLoggerFactory` default. Loggers
  are created once per category and cached in statics — no DI-scope machinery:
  `ILogger` is singleton-shaped, and logging scopes plus `Activity` trace ids
  are ambient (`AsyncLocal` in the provider infrastructure), so a static
  logger picks up the host's per-request scopes whenever the call runs on the
  request's execution flow. Off-flow events (monitor sampling, timers) log
  without request scopes, correctly. Whether scopes render is host logging
  config (`IncludeScopes`), not runtime concern.
- **No `IServiceProvider` in the runtime.** Holding the container "for future
  extensibility" is service location: the dependency list disappears from
  signatures, root-vs-scoped lifetimes trap, and `GetService` nulls turn
  missing registrations into silent degradation — against explicit ownership
  and fail-near-the-source. Future needs extend the options type property by
  property. If application-code DI ever becomes a compat requirement, its
  surface is `HttpRuntime.WebObjectActivator` (Framework 4.7.2+), a separate
  feature, not this seam.
- **The option-3 `EventListener` bridge is dropped** — the direct `ILogger`
  leg replaces it with no serialization round-trip and the `Exception` intact.
  The forward into `ILogger` never throws (`try/catch` around it): a failing
  log provider must not recursively fail the request, the follow-up's
  verification requirement. Kestrel has had exactly that bug
  (<https://github.com/dotnet/aspnetcore/issues/3460>).
- **One surgical addition to imported code**, to be surfaced for approval
  before landing (hotfixes-stay-minimal rule): `WebBaseEvent.RaiseRuntimeError`
  (`WebEvents.cs:402`) writes a `RuntimeError` event on the choke point
  *before* the `HealthMonitoringManager.Enabled` gate. That single site makes
  all 14 request-error paths portable and config-independent, mirroring
  ASP.NET Core hosting's unconditional unhandled-exception log, without
  touching the other ~42 raise sites. Ledger + provenance deviation entry
  either way.
- **No factory supplied** (embedding without the adapter, unit tests):
  `NullLogger` discards the `ILogger` leg, the `EventSource` leg still fires,
  events stay reachable out-of-process via EventPipe, the request is
  unaffected. The parity harness (`RuntimeDiagnosticListener`) remains the
  attach pattern for logger-less hosts.
- **Unchanged from the original recommendation**: health-monitoring policy
  (option 5), `EtwTrace` and `PerfCounters` dispositions, metrics on
  `System.Diagnostics.Metrics`, a future `ActivitySource` being a separate
  decision, and the open redaction question — Framework wrote full exception
  text with stack traces to the event log (`Misc.cs:76-92`), so content parity
  argues for full text on the event; filtering belongs to the host's logging
  pipeline.

### On the `ILogger` proposal

Accepted, with one earlier pushback retracted and one kept. Retracted: keeping
`Microsoft.Extensions.Logging.Abstractions` out of the runtime — the custom
seams that avoided it (option 4 and its single-method variant) reduce to
re-implementing `ILogger`, and port consumers are Kestrel-hosted and carry the
dependency regardless. Kept: `ILogger` does not replace the `EventSource`; it
joins it. The deep sites are static imported code either way, so the logger
lives behind the same static choke point the `EventSource` already is, and the
combined shape remains how ASP.NET Core itself reports the same conditions.
